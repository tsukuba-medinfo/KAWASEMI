# 施設向け：ID解決(resolver)・crosswalk 要件チェックリスト（別紙）

本書は KAWASEMI のデータ自動収集で用いる **ID解決系（resolver）と名寄せ表（crosswalk）**
に対し、施設側システム部門・ベンダーへ提示する要件チェックリストです。実接続パイロットや
本番導入の調整でそのまま配布できます。背景・設計思想は
[`key_resolution_guide.md`](key_resolution_guide.md) を参照してください。

## 前提（KAWASEMI 側の設計）

- KAWASEMI は crosswalk（登録番号 → 各システムの患者キー）を**保持・キャッシュしません**。
  可用性・整合性は resolver（施設側）の責務です（取り違え防止のため意図的にキャッシュを持たない）。
- resolver 不通・タイムアウト・認証失敗・応答不正は**自動収集を停止**します（誤った患者値を
  取るより何も取らない）。したがって resolver の可用性が収集運用のボトルネックになります。

### resolver の実装は院内 FHIR の identifier 検索1つです

**現時点で resolver を別プロセスへ委譲する経路はありません。** KAWASEMI は施設の FHIR サーバへ
`system|登録番号` で Patient を検索し、その `identifier` から各 key_type の値を得ます。したがって
本書のチェック項目は、**施設の FHIR サーバに対する要件**として読んでください（接続設定は
`FHIR_SERVER_URL` / `FHIR_SERVER_TIMEOUT` / `FHIR_AUTH_MODE` ほか）。

以前は `KEY_RESOLVER_BACKEND=http` で名寄せ系を別プロセスへ物理隔離できる設計を持っていましたが、
選ぶ利用者が現れなかったため実装を削除しました。**別プロセス化は将来案**として
残っており、必要になった時点でワイヤ契約（§5）と一緒に実装し直します。本書の §5 は、そのときに
施設へ提示する契約の草案として残しています。

## 1. 可用性

- [ ] 自動収集を行う**運用時間帯**を定義した（例: 平日 9:00–18:00）。
- [ ] その時間帯の **稼働率目標（SLA）** を合意した（例: 99.5% 以上）。
- [ ] 冗長構成（HA）または計画停止のスケジュールと事前通知手段を定めた。
- [ ] 計画停止中は自動収集が `failed` になる前提を運用者が理解している。

## 2. 応答時間

- [ ] 1リクエスト（1被験者・複数 key_type の一括解決）の **応答時間目標**を合意した。
- [ ] KAWASEMI 側タイムアウト `FHIR_SERVER_TIMEOUT`（既定 30 秒）に**収まる**ことを確認した。
- [ ] バッチ解決（実行前に必要 key_type を一括）を前提とした負荷を見積もった。

## 3. ヘルスチェック・監視

- [ ] resolver に**ヘルスチェックエンドポイント**（または疎通確認手段）がある。
- [ ] 施設側で resolver の死活・エラー率・応答時間を監視する仕組みがある。
- [ ] 障害時の**連絡経路・エスカレーション先**を運用者と共有した。

## 4. 認証・秘匿

- [ ] 認証方式を選定した：`none` / `bearer` / `basic`（`FHIR_AUTH_MODE`）。
      院内 NW を越える経路には **mTLS またはトークン認証を推奨**。
- [ ] トークン/鍵の**発行・ローテーション手順**と失効時の連絡を定めた。
- [ ] 認証を有効化する場合、資格情報が欠けていると KAWASEMI 側は resolver 呼び出し時
      （autofill 実行時）に fail-fast し当該実行が `failed` になる（無認証送信しない）ことを理解している。
- [ ] 認証秘匿値は KAWASEMI のログ・例外に出力されない（施設側ログでの取り扱いも確認）。

## 5. 応答仕様（ワイヤ契約）— 別プロセス化する場合の将来案

**現在の実装（院内 FHIR の identifier 検索）ではこの節は適用されません。** 名寄せ系を別プロセスへ
隔離する要求が出たときに施設へ提示する契約の草案として残しています。
下の `status` の3値と「未登録は `not_found`・一意化不能は `ambiguous`」という規則は、
FHIR 経路でも KAWASEMI 内部の扱いとして同じです。

- [ ] リクエスト `{"context": {"study_id": ...}, "subject": "<登録番号>", "key_types": [...]}` を受理する。
- [ ] レスポンスは key_type ごとに `status`（`found` / `not_found` / `ambiguous`）を返す。
- [ ] **未登録被験者は `not_found`** を返す（空応答・エラーで代替しない。区別が運用判断に必要）。
- [ ] **一意化できない場合は `ambiguous`** を返す（KAWASEMI は自動選択しない。一意化は resolver 側責務）。
- [ ] 要求した key_type が応答に欠けても可（KAWASEMI 側で `not_found` 補完する）。

## 6. crosswalk の整合性

- [ ] 登録番号 → 各 key_type の対応が**一意**であることを保証する運用がある
      （重複は `ambiguous` として返し、名寄せ元で解消する）。
- [ ] crosswalk の更新（新規被験者の登録・訂正）の**反映タイミング**を合意した。
- [ ] 誤った対応が発覚した場合の訂正手順と、影響した収集の再実行手順を定めた。

## 7. key_type カタログの整合

- [ ] 施設の患者キー名前空間（`mrn` / `dwh_serial` / `fhir_patient_id` 等）を洗い出した。
- [ ] `key_types.yaml` の id を（可能なら）FHIR `identifier.system` URI と整合させた。
- [ ] resolver が返す key_type 名と `key_types.yaml` の id が一致している。

---

### 障害時の運用（要約）

障害シナリオ別の確認・復旧手順は [`key_resolution_guide.md`](key_resolution_guide.md) §8 を参照。
要点は以下の通り：

| 事象 | 波及 | 復旧後の再開 |
|---|---|---|
| resolver 不通・timeout・5xx・認証失敗・応答不正 | 実行全体が `failed` | 復旧確認 → trial run で疎通 → 本番再実行（患者値未書込のため安全） |
| ある被験者が `not_found` / `ambiguous` | その項目のみ `needs_input`、実行は `partial` | crosswalk 登録・一意化 → 該当被験者を個別再実行。不能なら手入力へ縮退 |
