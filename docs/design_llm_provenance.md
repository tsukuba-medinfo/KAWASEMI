# 設計ロールの LLM 来歴

設計ロールの LLM 呼び出しについて、プロンプト全文と生応答を保存する。本文書はその
**根拠**（なぜ保存してよいのか）と**ガード**（前提が崩れる経路をどう止めるか）を記録する。

## 何が問題だったか

実行ロール（`llm_extract` / `llm_judge`）は evidence trace に
`llm{model, options, prompt, raw_output}` を残すのに対し、設計ロールは `llm_model` の
文字列しか残していなかった。プロンプトも生応答も DB にもファイルにも保存されず、ログにも
出さない。JSON パース失敗時ですら本文を載せない（`llm_json.py` の PHI 保護方針）。

その結果、**「LLM が何を読んでその記述にしたか」を後から確認できない**。人間レビューで
担保するという立場は取っていたが、レビューは「出てきた記述が妥当か」しか見られない。
記述の由来を検証するには入力と生応答が必要である。

臨床的意味の人が書いた版と自動生成版を独立に作って比較する用途では、**LLM が規約文書のどこを読んだか**が
比較の対象そのものになる。

## 保存してよい根拠：設計ロールの入力に患者データが含まれない

実行ロールの PHI 保護方針（生応答をログ・例外に載せない）は**変えていない**。設計ロールを
例外とするのは、入力の性質が違うからである。

| 設計ロール | 入力 | プロンプトへ入れる索引の中身 | 患者データ |
|---|---|---|---|
| 臨床的意味（step1-A）| 規約文書（入力マニュアル・記入の手引き・実施計画書）＋項目名 | `search_text`（チャンク全文）| 非該当 |
| データ所在（step1-B）| 索引（DB スキーマ定義・マスタ語彙・reference 文書）＋項目名 | `snippet`（抜粋）| 非該当 |
| 取得手順書（step2）| 項目名・所在記述・臨床的意味 | なし | 非該当 |
| 取得プラン（step3）| 上記＋確認済み手順書 | なし | 非該当 |

**4ロールとも配線済みである**。
索引の中身を読まない2ロールは `declare_content_sources` を呼ばない。

いずれも**施設の構造（どこに何があるか）と規約（何を書くべきか）**を入力とし、被験者の
値を読まない。設計ロールは患者を特定せずに動く（患者IDを引数に取らない）。

同じ論法の前例が索引側にある。indexer（`indexer/`）の DB 定義書取り込みは「DB 定義書は
患者データを含まない」という前提のもとで全文をプロンプトへ渡している
（`indexer/kawasemi_indexer/ingestion/pdf_doc.py`）。

対照的に、実行ロールは患者の原資料（叙述テキスト・OCR 結果）をプロンプトへ入れるので、
生応答も PHI を含みうる。**両者を分ける線は「患者を特定して値を読むか」である。**

## 前提が崩れる経路とガード

前提は「設計ロールの入力に患者データが混ざらない」である。崩れうる経路は3つある。

### 1. 患者データを含む文書が誤って reference 索引に入る

`docs/resource_index_guide.md` は `--file-source` に「患者データを含まない共通文書のみを
置くこと」と定めているが、運用ミスは起こりうる。混ざると、典拠探索が患者の記述を抜粋として
プロンプトへ入れる。

**この経路を止めるのは索引側の入口制限であって、本モジュールのガード2 ではない。**
ガード2 は下記のとおり別の不変条件を見ており、この脅威は検出できない。

#### 記録（`content_sources` 列）

プロンプトへ**原資料の中身**を埋め込んだ設計ロールは、その出所を
`declare_content_sources` で宣言し、`content_sources` 列に残す。監査側は「この来歴が
どの種類の資料の中身を読んだか」を行ごとに確認できる。**混入が起きたとき、事後に
それを追える記録がここに残る**というのがこの仕組みの主な効能である。

**何を「中身」と数えるか。** `snippet` が非空であることは中身を見せたことを意味しない。
`kind=file` の `snippet` は索引の作り方で二重の意味を持つ。

| ビルダ | 何を索引するか | `snippet` の中身 | payload |
|---|---|---|---|
| `build_reference_units` | 本文をチャンク化 | 本文の抜粋 | `path` ＋ **`char_range`** |
| `build_manifest_units` | **索引しない**（所在宣言のみ） | `path_pattern` ＋ notes | `path_pattern` ＋ `extract`（`char_range` なし） |

患者データファイルは**所在候補として正当**なので、後者がデータ所在ロールの候補に入るのは
正常系である。そこで `kind=file` は **`char_range` を持つときだけ中身**として宣言する
（`db` / `fhir` / `master` はスキーマ定義・コード表なので従来どおり kind だけ記録する）。

初版はここを「snippet があれば中身」と同一視していた。所在宣言ユニットが候補に入った
瞬間にガードが発火し、`system` ロールの来歴が `logger.error` 以外の痕跡なく失われていた。
その前の版（プロンプト全文から `{patient_id}` を探すマーカー方式）も、同じ性質の誤り
（正常系で必ず発火し、本来の脅威では発火しない）だった。

#### 検査（ガード2 = `_guard_content_sources`）

宣言された**中身つき**ファイルユニットの `file_role` が `reference` 以外なら**保存を
拒否する**（1件でも混ざればそのバッチ全体を保存しない。混入の疑いがある状態で一部だけ
残すと、後から何が保存されたかを判断できない）。

**これは索引の不変条件検査であり、indexer が作る正しい索引では原理的に発火
しない。** `build_reference_units` は `char_range` と `file_role=reference` を必ず同時に
付けるので、「中身つきなのに reference ではない」ユニットは索引の契約上作られない。
発火するのは索引ビルダかプロンプト構築が壊れたときだけである。

**したがって、本節の見出しにある脅威（患者データを含む文書が reference として索引される）
をガード2 は検出できない。** その文書は正しく `file_role=reference` の中身つきユニットに
なるので、検査を素通りする。この脅威は次の2つが担う。

- **索引側の入口制限**（`docs/resource_index_guide.md` §4.3 の「患者データを含まない共通
  文書のみを置くこと」）。患者データのファイルは `--file-source` ではなく
  **file manifest（所在宣言のみ・中身を索引しない）** として扱う（同梱の E2E 試験環境では
  `examples/e2e/file_manifest.jsonl`）
- **`content_sources` 列の記録**（事後の監査）

同様に、人が自由記述する臨床的意味の記述・手順書の説明欄・所在候補の手入力に被験者の
実データを書いた場合も検出できない（構造を伴わないため）。**これらも索引側の入口制限と、
記入者への周知という運用で担保する範囲である。**

**効かない防御を層として数えないこと。** ガード2 は「索引が壊れていないこと」を保証する
だけで、患者データ混入に対する防御層としては数えない。臨床的意味の典拠探索は
`is_citable_reference_unit` により `file_role=reference` の本文に絞られているが、これも同じく
「reference 宣言が正しい」ことに依存しており、混入そのものを止める層ではない。

### 2. 実行ロールの来歴がこのテーブルへ流れ込む

**ガード（`DesignLlmRecorder.__init__` と `save_design_llm_calls` の両方）**: `role` が
`DesignRole.ALL`（clinical / system / runbook / plan）以外なら例外にする。**入口だけで
検査すると `recorder.role` の再代入で抜けられるので、保存時にも検査する**（層として
独立させ、入口の検査に依存しない）。加えて構造的に、実行ロールは `llm_json` を使わず
`executor.py` が自分で evidence trace へ書くので、この経路を通らない。

### 3. 保存内容が肥大して運用を壊す

**ガード（`design_provenance.py` の `_clip`）**: 1フィールド 64,000 文字で切り詰め、
`truncated=True` を立てる。切り詰めた事実を残すことで「全文がある」と誤認させない。

## 来歴の保存に失敗したときどうするか

**AI 成果物（プラン・手順書・草案）は落とさない**。ルートは
`save_design_llm_calls_safely` を使い、ガード発火・DB エラーのいずれでも例外を投げない。

理由は2つある。成果物は人間の確認を経て confirmed になるので、来歴の欠落が可視化されて
いれば判断できる。一方で成果物ごと中止すると、AI 呼び出しが失敗したパスでは元の
`AIServiceException.message` まで generic 500 に化けて、操作者が原因を追えなくなる。

ただし**「記録に失敗した」ことは必ず残す。** 黙って0件で通すと、後から
「AI を使っていない」と「記録に失敗した」が区別できなくなる。ログレベルで区別する。

| 事象 | レベル | 意味 |
|---|---|---|
| ガード2 の発火 | `error` | 混入の疑い。最も監査に残すべき事象 |
| その他の保存失敗（DB エラー等） | `warning` | 記録の欠落 |

**この区別が残るのはサーバログだけであり、確認書には現れない。** 確認書の開示欄
（下記）は `ai_input_design_llm_calls` の**保存済み行**を役割ごとに集計するので、ガード
発火や DB エラーで保存されなかった呼び出しは、行が無い＝集計に出ない。したがって確認書
だけを見ると「その役割で AI を使っていない」と「記録に失敗した」は区別できない。

これは意図した限界であり、対応していない。記録の失敗は運用上まれで、起きたとき
にはサーバログ（`error` / `warning`）で検知して原因を除去する前提を採る。確認書に
「記録失敗 N 件」を出すには失敗そのものを別テーブルへ永続化する必要があり、
「来歴の保存に失敗しても成果物を落とさない」という方針と釣り合わない規模になる。
**確認書の数字を「設計で AI を呼んだ回数」と読んではならない**（読めるのは「来歴を保存
できた回数」である）。

## 保存されるもの

`ai_input_design_llm_calls` テーブル（`DesignLlmCall`）。

| カラム | 内容 |
|---|---|
| `role` / `label` | 設計ロールの区分と処理名（例 `runbook` / 「手順書生成」）|
| `model` / `options` | モデル名と生成 options（temperature / num_ctx / seed）。再現性の記録 |
| `provider` | 推論プロバイダ（`ollama` 等）。**モデル名だけでは実装が特定できない**ため別に持つ |
| `model_digest` | モデルの**中身**のダイジェスト。**タグだけでは中身の差し替えが記録に出ない**ため別に持つ |
| `model_digest_unavailable` | ダイジェストが取れなかった理由。**理由入りと null は違う**——理由入りは「引いたが取れなかった」、両方 null は「宣言していない」 |
| `index_build_info` | 検索に使った索引の `build_info`。索引は版管理外なので**使われた瞬間の記録**だけが同一性を残せる。索引を読まないロールでは null |
| `duplicated_link_ids` | 同じ項目に複数のエントリが返った `link_id`。**サーバ側の真実**として応答をマージした直後に記録する。空配列＝重複なし、null＝未記録 |
| `think` | thinking を要求したか。**`options` には入らない**——`think` は `/api/chat` のトップレベル引数である。渡さないとモデルの既定に従うので、Ollama やテンプレートの更新で測定が黙って動く。既定値は `llm_json.DEFAULT_THINK` |
| `thinking` | モデルが返した**推論本文**。`content` と別のフィールドで返るので JSON は汚れないが、時間と `num_ctx` を消費し出力に影響する。**`think` と対で要る**——`think=True` でもモデルが何も考えないことはありうるので、`thinking` が空であることだけでは「切っていた」と区別できない |
| `endpoint` | 呼び出し先の base URL。**所要時間はマシン依存**なので、時間だけ残しても比較できない。取れなければ null |
| `timing` | 所要時間。`elapsed_ms`（クライアント側の壁時計）と、Ollama が返す内訳（`total_duration` / `load_duration` / `eval_count` / `eval_duration` / `prompt_eval_count` / `prompt_eval_duration`、ナノ秒）。**設計の処理時間の唯一の出所**で、行は生成後に1度だけ作られるので `created_at`/`updated_at` の差からは出せない。**`load_duration` が別に取れるのが要点**——初回コールのモデルロードを差し引けないと、逐次で回したとき1本目のモデルだけ遅く見える |
| `system_prompt` / `user_message` | プロンプト全文 |
| `raw_output` | 生応答（パース前）。**失敗時も残す** |
| `error` | 失敗理由（成功時は null）|
| `chunk_index` / `item_count` | 分割呼び出しの何回目・何項目か |
| `truncated` | 保存上限で切り詰めたか |
| `created_by_id` | 生成を実行した操作者 |

**失敗した呼び出しも記録する。** パースできなかった応答そのものが、モデルが何を返したかの
唯一の手掛かりになる。ログには相変わらず載せない（方針は不変）ので、DB が唯一の記録に
なる。

#### ダイジェストを別に持つ理由（`model_digest` 列）

**タグは実装を特定しない。** `provider` を足しても、**同じタグの中身が差し替わる**経路は
残っていた——`ollama pull` で上流のタグが更新された場合と、ローカルで同名タグを作り直した場合
である。どちらも `model` 列は同じ文字列（`model-a:7b` 等）のままなので、**2回の実行を記録だけ
では区別できない**。

取得経路は Ollama の `list()`（`/api/tags`）である。**`/api/show` は `digest` を持たない**
（`ShowResponse` のフィールドは `modified_at` / `template` / `modelfile` / `license` /
`details` / `modelinfo` / `parameters` / `capabilities`。実測）。

**取得に失敗しても生成は続ける。** 理由は `provider` と同じで、来歴の検証が測定を壊しては
ならないためである（多数の項目を生成する途中で推論サーバへの1回の往復が失敗したときに、成功した
生成を捨てる理由は無い）。取れなかったことは `model_digest_unavailable` に理由として残るので、
**「宣言していない（両方 null）」とは区別できる**。

**`/v1/models` だけを持つ OpenAI 互換のアダプタは、常に理由つきの null になる。** 一覧に
`id` / `created` / `owned_by` などは載るが、**digest に相当するフィールドが無い**。したがって「サーバが一覧を持たない」のではなく「**一覧に
中身の同一性が載っていない**」のが理由である。アダプタが `model_digest(model)` を実装すれば
そちらが優先される。

#### プロバイダを別に持つ理由（`provider` 列）

**モデル名は実装を特定しない。** `OLLAMA_MODEL` は環境変数で上書きできる。さらに同じモデル名を別の推論
エンジンが名乗ることもできる（Ollama で動かないモデルを OpenAI 互換や Anthropic 互換の専用サーバ経由で
呼ぶ場合など）。このとき `provider` が無いと、記録は Ollama で測ったものと区別できない。

`provider` は**設定値ではなく、呼び出しに使う client 自身**（`provider_name`）から取る
（`kawasemi/ai_input/llm_provider.py`）。設定を別に持つと、client を差し替えたのに設定を
直し忘れた記録が嘘をつく。実行ロールは DB ではなく evidence trace に残すため、同じ粒度で
`llm.provider` を持つ。

**取得の関数は例外を投げない。** 名前が長すぎる等はアダプタ側の実装の誤りで、それは構築時に
`validate_provider_name` が落とす。来歴の検査を呼び出しの途中で投げると、**成功した生成の
記録を壊す**——実測で、生成成功後の trace 組み立て中の例外が抽出値と生出力の両方を捨て、
送信前の例外が「送った」として3状態会計（`answered + failed + unattempted`。`llm_json.PartialResultException`）を破った。**来歴の検証が測定を壊してはならない。**

**記録しただけでは足りない。** データ収集手続確認書の設計ロール来歴の表に**プロバイダの列**を
出す（`kawasemi/web/templates/ai_input/validation/*/validation.html`、集計は
`routes.py` の `design_llm_provenance`）。実行ロールは trace の `LLM` 行に `provider=` を出す。
ここに出さないと、別エンジンで測った run の確認書が Ollama の run と1バイトも変わらず、
**監査者が「どのエンジンがこの測定を出したか」に答えられない**。列に入っていても、直接 SQL を
叩ける人しか読めないなら比較可能性の役に立たない。

**この列は測定値の比較可能性のための記録である。** プロバイダを変えれば典拠の付与率などの
実測値は測り直しになる。

分割呼び出し（`chat_json_chunked`）は1チャンク1レコードになる。どのチャンクでどの項目を
渡したかが分からないと、記述と入力を突き合わせられない。

## 確認書での開示

データ収集手続確認書の「設計過程におけるAI利用」開示欄は、従来 `llm_model` の集合と
`status` だけを出していた。ここに**来歴の件数と内訳（役割ごとの呼び出し回数・失敗件数・
切り詰め件数）**を加える。プロンプト全文は確認書に載せない（文書が肥大するため）が、DB に
あることと参照方法を示す。

数えるのは `ai_input_design_llm_calls` の**保存済み行**である。前節のとおり、保存に失敗
した呼び出しは本表に現れない。テンプレートにもその旨を注記してある。
