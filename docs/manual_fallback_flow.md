# manual 縮退フロー（正本）

最終更新日: 2026-07-20

本書は「自動取得できない項目を `manual`（手動入力）へ落とす」縮退の、判断・承認・記録・
手入力・検証の一連の手続きの **正本（source of truth）** である。これまでコードの暗黙挙動に
依存していた縮退を、担当ロール付きの運用手順として固定する。

実装参照:

- `kawasemi/ai_input/models.py` — `SourceCategory`（`manual` と `not_available` の区別）、
  `SystemLocation.is_resolved` / `has_content`（未調査と確定の判定）
- `kawasemi/ai_input/schemas.py` — `source_category` の既定値が `"manual"` であること
- `kawasemi/ai_input/compiler.py` — プランコンパイラのプロンプト厳守事項4
- `kawasemi/ai_input/executor.py` — `needs_input` スキップと `FailureCode.NEEDS_INPUT`。
  `guard` による全スキップの `FailureCode.NOT_APPLICABLE`（**縮退の根拠ではない**）
- `docs/roles_and_permissions.md` — ロール×機能の権限（縮退フローの権限マトリクスを含む）
- `kawasemi/ai_input/metrics.py` — 取得困難度メトリクス（FailureCode と項目別集計）

## 1. 状態の区別: 「未調査の manual」と「確定した manual」

`source_category` の既定値は `"manual"` であるため、値としての `manual` だけでは
「まだ調べていない」と「調べた結果、自動取得しないと決めた」を区別できない。
運用上は `SystemLocation.candidates` への明示登録で区別する:

| 状態 | candidates | 実装上の判定 | 意味 |
|---|---|---|---|
| **未調査** | 空（未登録） | `is_resolved == False` | 誰も所在を調査・決着させていない。既定値の `manual` はこの状態であり、確定ではない |
| **確定した manual** | `manual` 候補を明示登録 | `is_resolved == True` | 調査の結果「自動取得せず手動入力とする」と人が決着させた |
| **データ不存在** | `not_available` 候補を明示登録 | `is_resolved == True`, `has_content == False` | 施設にそのデータ自体が無い。手動入力の対象でもなく、手順書・プランを生成しない |

step1-B の画面上はどちらも `manual` に見えるため、**確定の際は理由区分（§2）を
location 欄に必ず記載する**（`docs/ai_mode_guide.md` のステップ1-B の注記を参照）。

この記載は文書規約であると同時に**実装上のスイッチ**を兼ねる:
`has_content` は location が空の `manual` 候補を False（手順書・プラン生成の対象外＝
`not_available` と同じ扱い）と判定するため、**location を空欄のまま manual 候補を
登録すると「確定した manual」として手順書パイプラインに載らない**。手動入力手順を
取得手順書（step2）に反映させる（§3-5）には location への理由記載が必須である。

## 2. manual の理由区分（4区分）

確定した manual には理由区分を必ず残す。区分は取得困難度メトリクス（FailureCode）と
対応しており、実運用で「なぜ取れないか」を横断集計する際の人手側の区分になる。

| 区分 | 意味 | 現行の表現方法 | 縮退前の失敗傾向（FailureCode） |
|---|---|---|---|
| **データ不存在** | 施設にそのデータが無い | `not_available` 候補で確定（manual ではない） | `not_found_for_patient` が全患者で継続 |
| **取得手段なし** | データは存在するが接続・抽出経路が無い | `manual` 候補＋location に「理由: 取得手段なし（…）」 | `source_unavailable` / `schema_mismatch` |
| **品質不足** | 取れるが信頼できない（OCR 誤読・自由記載の曖昧さ等） | `manual` 候補＋location に「理由: 品質不足（…）」 | `extraction_low_confidence` |
| **未調査** | 既定値のまま（確定状態ではない） | candidates 未登録 | （メトリクスに現れない） |

**`not_applicable` はこの表のどの区分にも対応しない。** 「患者の文脈上そもそも該当しない」
は人手入力で埋める対象ではないので、**縮退（manual 化）の根拠にしてはならない**。区分の判断は
被験者によらない施設の性質（データ不存在・取得手段なし・品質不足）で行う。

「縮退前の失敗傾向」列は、その区分で縮退を提案する根拠になりやすい FailureCode を示す。
なお取得困難度メトリクスの集計は **evidence に現れた項目のみ**を数えるため、未調査項目（プラン未生成・
未実行）は集計の分母に現れない。実行時に `needs_input` が付くのは主に
**縮退確定済み項目（空 steps のプラン）** が autofill 対象に含まれたときである
（`guard` で取得側が全スキップになった項目のうち、**判定 op を経たものは `not_applicable`**、
経ていないものは `unclassified` になる）。

理由区分を `system_locations` の構造化フィールドとして持たせるか（alembic migration 要）は、
実運用で区分の妥当性を検証してから判断する（§6）。本書の時点では
**文書規約（location 欄への記載）** で運用する。

## 3. 判断主体と手続き（SoD 準拠）

「ある項目を自動取得対象から外す」は収集設計の変更であり、1人で完結させない。
**収集者（collector）が manual を確定してはならない**（設計の確定は収集者が持たない）。
4役割では設計の4段階はすべて設計者（designer）の権限なので、提案・承認・確定操作の分離は
**役割ではなく様式への担当の割り当て**で表す（臨床的意味を書く人と所在を決める人を分ける必要が
あるときは、同じ様式に設計者を複数置き、どの段階を誰が担当するかを施設の運用記録に残す）。

```
（根拠収集）        （提案）              （承認）              （確定操作）
メトリクス      →  設計者（手順書・    →  設計者（臨床的      →  設計者（所在の担当）が
試行実行の結果      プランの担当）が提案    意味の担当）が承認      step1-B を更新
```

| 手続き | 担当（設計者のうち） | 内容 |
|---|---|---|
| 1. 根拠収集 | 手順書・プランの担当 | 取得困難度メトリクスの failure_code 内訳、autofill 試行の結果を確認する |
| 2. 提案 | 手順書・プランの担当 | 「自動取得不能」を理由区分（§2）付きで提案する。所在同定の誤り（`schema_mismatch`）は即縮退せず、まず所在調査のやり直し（step1-B / 索引再確認）を検討する |
| 3. 承認 | 臨床的意味の担当 | 臨床的必要性と人手収集の負担を判断して承認する。承認の記録は運用記録（施設の様式）に残す |
| 4. 確定操作 | 所在の担当 | 承認に基づき step1-B（`/ai-input/.../system`）で `manual`（または `not_available`）候補を登録し、location 欄に理由区分・承認日を記載する |
| 5. 手順書更新 | 手順書・プランの担当 | 該当項目の取得手順書（step2）を手動入力手順（原資料の所在・転記方法）へ書き換え、確認済みにする |

- 技術的に強制されるのは「収集者・閲覧検証者・管理者は step1-B を編集できない」（`RequireDesigner`）
  までである。承認と確定操作の分離は**運用統制**（担当の割り当てと運用記録）で担保する
  （`docs/roles_and_permissions.md` の SoD の節）。
- 承認記録と `system_locations` の更新履歴（updated_at）を突合できるよう、
  location 欄には承認日を含める（例: `理由: 取得手段なし（読影レポートは外部PACS、接続経路なし）承認: 2026-07-20 臨床的意味の担当者名`）。

## 4. 収集者（collector）の手入力手順

1. autofill（本番実行）後、manual 確定項目・`needs_input` 項目はフォーム上で空欄のまま残る
   （executor は未確定 op・manual プランを実行せずスキップし、evidence に
   `failure_code: needs_input` を記録する）。
   **`not_applicable` の項目も空欄で残るが、これは手入力の対象ではない**（患者の文脈上
   そもそも該当しないと判定された項目。`guard` による全スキップ）。**空欄だからと値を入れない**
   こと——入れると人手介入として数えられ、取得困難度の測定を汚す。判定が誤っていると考えられる
   場合は §3 の手続きで設計側へ差し戻す。
2. 収集者は取得手順書（step2）の手動入力手順に従い、原資料（カルテ・紙帳票・
   外部システム画面）から転記して入力する。受け取った（有効なリースのある）症例のみ入力できる。
3. 回答の確定保存（記入責任）は収集者が行う。autofill 由来の値と人手入力の値は
   実行記録（`InputExecution.prefill_data`）との差分として後から突合できる
   （取得困難度メトリクスの人手介入率）。

## 5. 閲覧・検証者（reviewer）の検証観点（manual 項目は自動項目と異なる）

| 観点 | 自動取得項目 | manual 項目 |
|---|---|---|
| 根拠 | evidence（DSL実行トレース）で機械的根拠を確認できる | evidence が無い。**原資料との突合が唯一の検証手段** |
| 突合方法 | トレースの query / 生出力と回答値の一致 | 取得手順書に記された原資料の所在へ遡り、記載値と回答値を照合する |
| 典型的な誤り | 所在同定の誤り・抽出パスの誤り | 転記誤り・単位の取り違え・日付形式の揺れ |
| SoD | 入力者（autofill 実行者）と検証者の分離（実装済み） | **入力者と検証者の分離は同様に必須**（自己検証禁止） |

## 6. 実接続での縮退運用

実接続で取得不能項目が発生したときの受け皿は本フローとする:

1. **記録**: 取得困難度メトリクスに failure_code が自動記録される
2. **分類**: failure_code 別に対処を分ける
   - `schema_mismatch` → 所在調査のやり直し（即縮退しない）
   - `source_unavailable` → 接続・認証の復旧（運用対応）
   - `not_found_for_patient` → 欠測か「データ不存在」かを臨床的意味の担当（設計者）が臨床的に判断する。
     `not_available` で確定する場合も **§3 の手続き（提案 → 承認 → 確定操作）に従い**、
     1人の単独直裁とはしない
   - `extraction_low_confidence` → プラン改善を試み、改善不能なら「品質不足」で縮退提案
   - `not_applicable` → **対処不要**（該当しないので取得しなくて正しい。自動充足率の
     分母から除かれている）。**縮退の根拠にしてはならない**。判定そのものが誤っていると疑う
     場合は、縮退ではなく所在・プランの見直しへ回す
3. **提案 → 承認 → 確定**: §3 の手続き
4. **手順書の更新**: §3-5（手動入力手順への書き換え）
5. **追跡**: 縮退後も取得困難度メトリクスの人手介入率で負担を定量化し、経路が整備されたら
   縮退解除（manual → 自動取得へ戻す。同じく §3 の手続きで行う）を検討する

運用結果の報告には、**理由区分（§2）を `system_locations` の構造化フィールドへ
昇格させるか（スキーマ化）の要否判断**を含めること。

## 7. 暗黙挙動の仕様化（コードとの対応）

以下のコード挙動を本書の仕様として固定する。変更する場合は本書を先に改訂する:

- **プランコンパイラ**（`kawasemi/ai_input/compiler.py` システムプロンプト厳守事項4）:
  manual 中心で自動化できない項目は、空の `steps` と `return: null` のプランを返してよい。
  接続先・表・カラムが特定できない step は推測せず `needs_input: true` とする（厳守事項1）。
- **実行エンジン**（`kawasemi/ai_input/executor.py`）: `needs_input: true` の step は
  実行せずスキップし、evidence に `failure_code: needs_input` を記録する。空 steps の
  プランも項目単位で `needs_input` に分類される（`derive_item_failure_code`）。
- **確認ゲート**（`kawasemi/ai_input/models.py` `PlanStatus`）: program に `needs_input` が
  残る限り confirmed へ昇格できず、ステップ4では confirmed のみ実行可能。
- **手順書対象外**（`kawasemi/ai_input/models.py` `SystemLocation.has_content`）:
  `not_available` は取得対象ではないため、手順書・プランを生成しない。
